# DSA-111 — `nph-dropdown-menu`: end alignment

## Goal
The `nph-dropdown-menu` opens `space/inline-tight` below its trigger, aligned to the start edge (`fichas/nph-dropdown-menu.md`, business rules; P92). The accepted drawing of the `nph-split-button` (DSA-109) puts the menu on the end edge of the group, which is the end edge of the arrow, its trigger (Pend. 9, accepted with the proposals). The design owner decided that the menu gains an end alignment, as the `nph-popover` has (item 9).

## Where the decision is
In the evidence of the `foundation-decision` gate: `docs/operacao/evidencias/DSA-111/foundation-decision-2026-11-23.md`. There is no need to open Figma.

## What changes
- A property for the alignment to the trigger, with the start edge as the default, so every menu today stays as it is, and the end edge. The `nph-popover` precedent is `align` (start, center, end; P111); whether the menu takes the same name and the same three values, or only start and end, is the code owner's choice.
- Logical edges: in a right-to-left page, the end is the left.
- The rest of the placement does not change: 4 px below, turning up when it does not fit below and fits above, never leaving the window, following the trigger on scroll and resize (P92, P126).
- The spec, the metadata and `docs/decisoes-tecnicas.md` (P92) record the new alignment.

## How it is proved
**`foundation-decision`** — passed. **`review-and-merge`** — a test for the end alignment, also turning up and near the edge of the window, and one that the default stays at the start; the proof commands in `docs/operacao/component-handoff.md` exit 0; merged into `v/5.0.0`.

## What this task does not do
It does not create a token. It does not add a nested menu. It does not build the split (DSA-109).
