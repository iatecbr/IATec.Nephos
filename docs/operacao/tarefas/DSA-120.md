# DSA-120 — Each component reads its own color tokens

## Goal
A count in the code at `c2e683aa` (2026-11-23) found 37 of the 61 components of that day
painting with semantic colors straight (`color/*`, `status/*`), and the icon with no token of
its own. The rule T9 asks for three layers: the component reads only its
own `<piece>/<property>` token, which points to the semantic token with the same role. This task
moves the CSS of the older components to the tokens that came in with this push. Each new token
points to the semantic token the component reads today, in both modes, so **nothing changes on
screen**, except the empty and error states of `nph-image` (section "nph-image").

The gain: a later change to one piece (for example the hover of the danger button) changes one
token and does not drag the other pieces that share the semantic token.

## The four rules (approved by Indiane on 2026-11-25)
- **R1, one token per variant, element, property and state that has its own color.** A state that
  repeats the default color uses the default token. Name: `<piece>/<variant>-<element>-<property>-<state>`.
  Example: `button/primary-solid-background-hover`. `tinted` names the background and the text
  that the outline, light and ghost emphases of `nph-button` share today (the same semantic token
  in the three).
- **R2, focus ring and halo, shadow and scrim stay global** (`focus/*`, `shadow/*`, `overlay/*`).
  Only the focus **border painted in the color of the variant** gets a piece token
  (`button/primary-focus-border`, `togglebutton/focus-border`, `navigation-menu/focus-border`);
  the halos stay `focus/halo-*`. The piece focus tokens that already exist (chip, tree, tabs and
  others) stay. `nph-accordion-item` changes from `collapsible/focus-border` and
  `collapsible/focus-halo` to `focus/border` and `focus/halo` for the colors (widths and radii
  stay `collapsible/*`).
- **R3, the icon takes the color of the parent piece.** Inside another piece the icon uses the
  same token as the text beside it; it gets an `-icon` token only when its color differs from
  the text (`label/info-icon`, `avatar/icon`, `date-picker/icon`, `combobox/create-icon`).
  `icon/foreground` and `spinner/foreground` are the colors of the piece on its own. See
  "Code decision 1".
- **R4, piece inside piece.** The parent creates its own token pointing to the semantic token,
  never to the token of the child. An override that repeats the child's default is removed (the
  child goes back to its own token). An override that differs points to a token of the parent.
  In Figma, where an icon swapped inside a button cannot drop its override without losing the
  color, the override points to the child token (`button/*-foreground`, `icon-button/*-foreground`).
  In CSS, this means: a parent that redefines a child variable (`--nph-color-*`, `--nph-button-*`)
  with the value the child already has by default removes that line.

## What changes in the code
For each component below, in its CSS: where a declaration reads a semantic color
(`var(--nph-color-*)`, `var(--nph-status-*)`) to paint an element that has a token in its table,
read the piece token instead. The token and the semantic token have the same alias, so the
computed color stays the same; the "Where" line says which element each token paints when two
tokens share an alias (for example `button/primary-solid-background` and
`button/primary-focus-border`, both `color/primary`).

A semantic color the CSS reads and the table does not cover stays as it is in this task (for
example `status/error` on the `nph-label` asterisk, the `status/help` icon of the `nph-select`
option, `color/secondary-foreground` in `nph-calendar` and `nph-navigation-menu`): Figma has no
approved token for it. List those in the pull request; they are not created in code.

Every `focus/*`, `shadow/*`, `overlay/*`, `state/*` and `scrollbar/*` read stays (R2).

## Code decision 1 (recommendation, does not block)
`nph-icon` and `nph-spinner` inherit `currentColor`. Setting `color: var(--nph-icon-foreground)`
on `:host` would break R3: every icon inside a button, a field or a menu would lose the color of
its parent. Recommendation: keep `currentColor` on both; use `icon/foreground` and
`spinner/foreground` where the piece stands alone (stories, docs examples and any place in the
library where an `nph-icon` or `nph-spinner` is not inside another piece). Spectrum and shadcn
inherit the icon color from the text; Carbon and Primer give an icon token only when it differs
(sources below).

## Default behavior
Keyboard, focus, pointer, events, aria, slots and properties do not change in any component: the
change is the name of the custom property each declaration reads. The combined states keep the
order they have today in each piece (disabled wins; then error; then focus; then hover; then
rest). Event, aria, slot, property and console warning stay with the code (Elvys), following the
APG and the Custom Elements Manifest.

Follows DSA-119 (resting border of the fields), DSA-95 (the option list outline is
`color/border-subtle`, now through `select/list-border` and `combobox/list-border`), DSA-90 D-12
(the date-picker gets its own tokens), DSA-51 D1 (answered above) and DSA-117 (`separator/border`).

## How it is proved
**`review-and-merge`** passes when the visual tests of the components above are green with the
same computed colors as before in light and dark (only `nph-image` empty and error change), the
tests that read a semantic custom property by name follow the new names, the specs, the metadata
and the comments follow, the proof commands in `docs/operacao/component-handoff.md` exit 0, and
the change is merged into `v/5.0.0`.

Tests: in the tests of each component above, search for the semantic custom property names
(`--nph-color-`, `--nph-status-`) and for the `collapsible/*` and `table/*` names read by
`nph-accordion-item` and `nph-data-table`; a test that asserts the name a declaration reads
changes to the piece token; a test that asserts the computed color does not change.

A quick check per component: in its CSS, no `var(--nph-color-*)` or `var(--nph-status-*)` is
left for an element that has a token in its table above.

## What this task does not do
- `nph-sidebar` and its items and the other `sidebar/*` tokens: DSA-121 covers the neutral
  sidebar; `sidebar/border` is in the table above.
- `nph-dialog`: no component set in Figma to read; it keeps `color/dialog*`.
- Spacing, radius, border width and size: color only.
- The pieces not listed (card, table, chip, tabs, stepper, tree, popover and the others) already
  read their own color tokens and do not change.
- No new token in code: a gap found in CSS goes back to Figma first.
